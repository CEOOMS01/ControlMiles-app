Document Intelligence: from odometer OCR to receipt reading

A shared, purpose-built extraction service for ControlMiles (odometer readings today, expense receipts next) and LedgiProof / Tax Pro (receipts and invoices for deduction records) — built once, not twice.

Drafted 2026-09-16 Scope: ControlMiles + LedgiProof + LedgiProof Tax Pro Status: awaiting 3 decisions below
Recommendation

Don't train a custom OCR/character-recognition model. Google ML Kit (already in ControlMiles, on-device, free) is the right text-detection engine — it already matches what MileIQ, Everlance, and every other serious mileage app use under the hood. The real, custom, defensible work is the layer above raw text detection: candidate scoring, validation, and — for receipts specifically — structured field extraction. ControlMiles' odometer reader already does this well for a single number; receipts need the same discipline applied to a whole document. Build that as one shared service both apps call, using a vision-capable LLM for the structured-extraction step (details in §4).

01

Where this actually stands today

Read odometer_ocr_service.dart (362 lines) before writing this plan — it's more capable than a first guess would assume.

Engine
google_mlkit_text_recognition, on-device, streamed per camera frame. Includes a hand-fixed NV21 buffer reconstruction (a real camera_android_camerax bug, not guessed) — the actual hard part of wiring ML Kit to a live camera stream is already solved.
Candidate scoring
Every 4–7 digit run in the frame is scored on digit count, ML Kit's own line confidence, and relative bounding-box size — not "biggest number wins" (a real bug this already fixed once).
Stabilization
Requires 3 consecutive frames to agree (±1%) before confirming a reading — rejects one-off misreads instead of trusting a single frame.

This is a single-scalar extraction problem: find the one number the driver is centering in frame. It's solved, and solved well. Receipts are a different problem — extracting several structured fields (merchant, date, total, tax) from a document whose layout varies by vendor — and the existing heuristic approach won't scale to that without a fundamentally different design.

02

The question you asked directly

"¿Podemos desarrollar nuestra propia función nativa de lectura por OCR?"

Technically yes. Practically, no — and here's the actual reasoning, not a deflection:

  • Google's and Apple's on-device text engines represent years of training on billions of real images, ship free, run with zero network latency, and improve with every OS update. Matching that from scratch is a multi-year ML research effort, not a sprint.
  • The real, ownable IP isn't character recognition — it's the domain logic wrapped around it. ControlMiles' scoring/stabilization layer is that custom function already. It's just currently scoped to one use case.
  • Receipts need a second capability text detection alone doesn't provide: document layout understanding — knowing that the number under "TOTAL" is the total, not the subtotal three lines above it. That's a different, harder problem than digit-finding, and it's where the plan below actually invests new engineering.
03

Two tracks, not one rebuild

TRACK Alow risk

Odometer — refine, don't replace

Keep odometer_ocr_service.dart as-is. If accuracy issues show up in the field, the fix is tuning existing constants (kMinConfidence, kStabilizeCount, the digit-score curve) against a small set of real dashboard photos — not a new architecture.

TRACK Bnew build

Receipts & invoices — one shared service

A small Supabase Edge Function (extract-document) that both ControlMiles and LedgiProof call with a receipt photo, returning structured JSON. Built once, tuned once, billed once — see §4–§6.

Recommended: vision-LLM extraction. 07

Data model

One shared shape, returned by the Edge Function, stored once, read by both apps with their own display logic on top.

{
  "document_id": string,
  "source_app": "controlmiles" | "ledgiproof" | "ledgiproof_taxpro",
  "document_type": "receipt" | "invoice" | "odometer",
  "merchant_name": string | null,
  "transaction_date": date | null,
  "subtotal": decimal | null,
  "tax": decimal | null,
  "total": decimal,
  "currency": string, // ISO 4217, default USD
  "suggested_category": string | null, // e.g. "fuel", "tolls", "maintenance"
  "line_items": [{ description, amount, quantity }] | null,
  "field_confidence": { [field: string]: 0.0-1.0 }, // per-field, never one blended score
  "needs_review": boolean, // true if any required field < threshold
  "raw_extraction": object, // full model response, kept for audit/debugging
  "image_url": string
}

field_confidence as a per-field map (not one overall score) matters here specifically because it's what lets the UI ask "is this the right total?" only when the total is actually uncertain, instead of nagging the user on every scan — same principle the odometer reader already applies with its stabilization buffer.

08

Security & privacy — non-negotiable, not an afterthought

  • Redact before storing, not after. A gas receipt or parking stub can carry a partial card number. The Edge Function's own prompt should instruct the model to omit any payment-card digits from the structured output entirely — don't rely on a downstream scrub step to catch what the extraction step already captured.
  • Row-Level Security from day one on the new table (per-user, per-organization for Fleet), matching the RLS pattern already proven across this session's other work — no exceptions for a "just for now" launch.
  • Rate-limit the endpoint the same way /governance/decision is rate-limited in CGC Core — an uploaded-image endpoint is a real cost/abuse surface if left open.
  • Raw images get a retention window, not indefinite storage — keep the structured JSON (small, needed for tax records) longer than the source photo (large, only needed to re-verify a disputed extraction).

Rollout

PHASE 11–2 weeks

Prototype against real receipts

  • 10–15 of your own real receipts/gas stubs, deliberately messy (crumpled, faded thermal paper, angled)
  • One vision-LLM call, hand-written prompt, no infrastructure yet — just measure field-level accuracy
  • Go/no-go gate: if total/date/merchant accuracy is below ~90% on this set, revisit the model choice before building anything else
PHASE 22–3 weeks

Shared Edge Function

  • extract-document function, the schema from §7, RLS-backed storage table
  • Confidence-threshold validation layer (§7) and the field-flagging UI pattern
  • Wired into ControlMiles Fleet expense capture first (smaller surface than LedgiProof)
PHASE 32 weeks

LedgiProof / Tax Pro integration

  • Same service, new caller — no new extraction logic, just LedgiProof's own category mapping and deduction rules on top of the shared schema
  • Real accountant review of a sample batch before this touches an actual client tax return
10

Three decisions only you can make

Which vision-LLM provider?
Compact-tier (Gemini Flash-class or GPT-4o-mini-class) is cheapest and likely sufficient per §5–§6 — but the actual accuracy call needs Phase 1's real-receipt test, not a spec sheet. Also worth weighing: does keeping this on Anthropic's API (the same relationship this whole build already runs on) simplify billing/vendor count enough to be worth a possible cost difference?
Where does extract-document live?
A new Supabase Edge Function on ControlMiles' own project (fastest to ship, but LedgiProof would call across projects), a new function on whichever Supabase project LedgiProof already uses, or a third option: hosted inside CGC Core's existing FastAPI backend as a new endpoint, reusing its already-built rate-limiting/RLS/tenant patterns instead of rebuilding them in Deno. This last option has the most existing infrastructure to lean on.
Confidence threshold for "needs review"?
Too strict and every receipt gets flagged (defeats the automation); too loose and a wrong total silently reaches a tax record. Needs a real number, tuned against Phase 1's test set — not guessed in advance.
